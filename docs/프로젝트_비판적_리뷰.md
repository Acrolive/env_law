## 1. 총평

`env_law`는 국가법령정보 OpenAPI를 단일 근거원으로 사용하고, 검색·검증·평가를 분리하며, HWP와 PDF를 교차 비교하는 환경 법령 조사 보조 시스템이다. 단순 대화형 데모보다 한 단계 발전한 구조를 갖추고 있으며, 실무에서 문제가 되는 출처·시행일·별표 변환 오류를 명시적으로 다룬다는 점이 강점이다.

다만 현재 구조는 **인용 진위를 재확인하는 법령 리서치 보조도구**에 가깝다. 조문의 적용 타당성과 법률적 결론까지 검증하는 시스템은 아니므로, `환각 0`이나 법률 결론 보증을 외부에 약속하기에는 근거가 부족하다.

## 2. 주요 강점

### 2.1 공식 API 중심의 근거 제한

- 국가법령정보 OpenAPI 응답으로 확인하지 못한 조문·판례·해석을 생성하지 않도록 명시했다.
- 법령명, 조·항·호, 공포번호, 시행일, 출처 URL을 강제한다.
- 확인 불가 시 확답하지 않는 실패 모드가 정의되어 있다.

### 2.2 API 사용의 표준화

`scripts/law_api.sh`가 법령·행정규칙·자치법규·판례·해석례 등 21개 target의 검색과 조회를 하나의 CLI로 표준화한다. MST와 ID 파라미터 차이를 래퍼 내부에서 처리한 점도 실무적이다.

### 2.3 별표 이중 파싱

- HWP/HWPX는 `kordoc`으로 Markdown/HTML 표로 변환한다.
- PDF는 `pdftotext -layout`으로 텍스트화한다.
- 두 결과의 유사도에 따라 `ok`, `warn`, `critical`, `fail` 경고를 부여한다.
- HWP, PDF, API JSON 각 120건을 수집하여 실증한 경험이 있다.

### 2.4 역할 분리와 자기비판 루프

검색, API 재검증, 3개 실무 관점 평가를 분리한 아키텍처는 하나의 대화 모델이 모든 결정을 즉시 내리는 구조보다 검토 가능성이 높다.

## 3. 핵심 한계와 위험

### 3.1 `환각 0` 목표의 과도한 표현

현재 verifier가 확인하는 것은 주로 다음 항목이다.

- 인용한 문자열이 API 응답에 실제 존재하는지
- 시행일이 현재 날짜보다 이전인지
- 출처 URL이 예상 형식을 따르는지

이 검증으로는 다음을 보증할 수 없다.

- 인용 조문이 해당 시설·매체·규모에 적용되는지
- 예외, 부칙, 경과규정, 다른 항의 단서를 누락하지 않았는지
- 상위법·시행령·시행규칙·고시 간의 연결이 완전한지
- 인용은 정확하지만 결론을 잘못 도출하지 않았는지

따라서 시스템의 목표는 `환각 0`보다 **근거 없는 인용과 시행 상태 오류를 자동 탐지하는 법령 리서치 보조**로 정의하는 것이 방어 가능하다.

### 3.2 LLM 자체 평가 90점의 타당성 부족

`persona-evaluator`는 환경공무원, 환경전문가, 사업장 전문가 관점에서 초안을 채점한다. 그러나 같은 LLM 체계가 생성한 답변을 다시 평가하므로 다음 한계가 있다.

- 전문가가 확정한 정답과 비교하지 않는다.
- 평가자 역시 법령 내용을 오해할 수 있다.
- 반복할수록 실제 정확도보다 형식적 완성도만 높아질 수 있다.
- 89점과 90점을 구분할 통계적·실무적 근거가 없다.

현재 점수는 품질 인증이 아니라 **내부 체크리스트 충족도**로 해석해야 한다.

### 3.3 별표 유사도 검증의 의미적 한계

`scripts/verify_annex.mjs`는 HWP 변환 텍스트와 PDF 텍스트에 공통으로 존재하는 3글자 조각의 비율을 계산한다. 이 지표는 대략적인 텍스트 유사성은 보여주지만 다음 오류를 놓칠 수 있다.

- 행과 열의 교체
- 기준값과 대상 시설의 잘못된 연결
- `이상`, `미만`, `초과` 등 부등호 의미의 변형
- 수치, 단위, 각주 위치 오류
- 병합 셀이 해체되면서 발생하는 의미 관계 손실
- 반복 문구에 의한 유사도 과대 평가

`파싱 성공 120건`은 파서가 결과를 생성했다는 의미이지, 120건의 표가 법적 의미까지 정확히 복원되었다는 의미는 아니다.

### 3.4 자동 테스트 부재 (작성 당시 — 현재 일부 보완)

작성 당시에는 자동 테스트가 없었다. 현재 `npm test`는 Codex 설정, 상태 단계, 평가 산술, 비밀정보 처리를 오프라인으로 검증하고 `npm run test:api`는 API 래퍼의 라이브 회귀 사례를 검증한다. 다만 다음 중 적용 타당성·골든셋·별표 의미 보존·실제 verifier 거부율은 아직 충분히 보호되지 않는다.

- API 응답 형식 변경과 오류 응답 처리
- target별 MST/ID 분기
- 조문 번호 정규화
- 현행·시행 전·폐지 법령 판정
- 캐시 TTL과 캐시 key 충돌
- HWP/PDF 파싱 실패 및 빈 결과 처리
- 잘못된 인용을 verifier가 실제로 거부하는지

법령 시스템의 위험도를 고려하면 추가 기능보다 테스트 구축이 먼저다.

### 3.5 실증 데이터의 대표성과 재현성

`scripts/crawl_annexes.py`는 검색어와 검색 결과를 무작위로 섞지만 고정 seed를 사용하지 않는다.

- 같은 조건의 재실행에서 같은 120건을 보장하지 못한다.
- 쉽게 파싱되는 문서가 과대표집되었을 가능성을 배제할 수 없다.
- 환경 법령에서 실무적으로 위험한 복잡 별표를 충분히 포함했는지 분명하지 않다.

무작위 120건 외에 다단 헤더, 병합 셀, 다중 각주, 세로 표, 다중 페이지 등을 구분한 **표 구조별 층화 표본**이 필요하다.

### 3.6 워크플로 규칙 불일치와 플랫폼 결합 (일부 보완)

- 반복 횟수는 현재 4회로 통일되었다.
- Codex용 `AGENTS.md`, `.agents/skills`, `.codex/agents`가 추가되어 Claude Code 단일 결합은 완화되었다.
- `scripts/harness_state.py`가 단계 순서, 필수 JSON 필드와 종료 상태를 강제한다. 다만 법률 evidence 내부 구조 전체를 JSON Schema로 검증하는 단계까지는 아니다.
- `.omc/state`에 현재 작업 상태와 과거 플러그인의 흔적이 함께 존재한다.

이런 불일치는 실행 플랫폼이 바뀌었을 때 재현성을 낮춘다.

### 3.7 보안과 비밀 관리

- `.env`와 `.claude/settings.local.json`을 Git에서 제외한 것은 적절하다.
- 그러나 `.claude/settings.local.json`의 과거 명령 허용 목록에 실제 OC가 포함된 URL 흔적이 남아 있다. Git에 추적되지 않더라도 복사·백업·화면 공유 과정에서 노출될 수 있다.
- 작성 당시 `scripts/law_api.sh`가 `.env`를 shell script로 실행했다. 현재는 `LAW_API_*` 전용 key-value 로더로 교체되어 이 실행 경로는 제거되었다.

## 4. 권장 개선 로드맵

### P0 — 신뢰성 기반 구축

1. `환각 0` 표현을 제거하고 시스템이 보증하는 범위를 명시한다.
2. 환경법 전문가가 정답·필수 근거·적용 조건을 확정한 질의 골든셋을 만든다.
3. API 래퍼, verifier, 시행 상태 판정에 대한 자동 테스트를 추가한다.
4. 인용 정확도, 필수 근거 재현율, 적용 조건 누락률, 시행 상태 오류율을 별도 지표로 측정한다.

### P1 — 별표 검증 고도화

1. 표의 행·열·셀·병합 정보를 구조화한다.
2. 수치, 단위, 비교 연산자, 각주를 별도 추출하여 교차 비교한다.
3. 복잡도 유형별 층화 표본과 의도적 실패 샘플을 추가한다.
4. `파싱 성공률`과 `의미 보존 정확도`를 별도로 보고한다.

### P2 — 워크플로 단순화와 재현성

1. 반복 횟수를 4회로 통일한다. **완료**
2. 검색·검증·평가 산출물에 JSON Schema를 정의하고 검증 스크립트를 추가한다.
3. 플랫폼 공통 규칙과 Claude/Codex 전용 설정을 분리한다.
4. 실증 데이터 수집에 고정 seed와 manifest를 사용한다.

### P3 — 보안과 운영 정리

1. 지역 설정·로그·히스토리에 남은 OC를 제거하고 필요하면 재발급한다.
2. `.env`를 shell `source` 대신 key-value 전용 로더로 읽는다. **완료**
3. 구조화된 로그에서 OC, 쿠키, 토큰과 같은 민감 값을 마스킹한다.
4. 로컬 상태와 재현 가능한 실증 산출물을 분리한다.

## 5. 권장 성과 지표

LLM의 자체 평가 평균 점수 하나보다 다음 지표를 독립적으로 관리하는 것이 적절하다.

| 지표 | 정의 |
|---|---|
| 인용 정확도 | 제시한 인용 중 API 원문과 일치하는 비율 |
| 필수 근거 재현율 | 골든셋의 필수 법령·조문 중 답변이 포함한 비율 |
| 적용 조건 누락률 | 시설·규모·시행일·예외 조건을 누락한 비율 |
| 시행 상태 오류율 | 시행 전·폐지·과거 법령을 현행으로 잘못 표시한 비율 |
| 출처 완전성 | 인용에 법령ID·시행일·URL이 모두 존재하는 비율 |
| 별표 셀 정확도 | 수치·단위·행·열 관계가 원본과 일치하는 비율 |
| 전문가 결론 일치율 | 골든셋의 결론과 시스템 결론이 일치하는 비율 |

## 6. 적절한 운영 포지셔닝

### 현재 단계에서 적합한 용도

- 환경 법규 담당자의 법령·판례·행정규칙 탐색 보조
- 관련 조문과 시행일의 1차 정리
- 별표 파일의 검색 가능한 형태로의 변환
- 최종 검토 전 근거 누락과 인용 오류 탐지

### 현재 단계에서 부적합한 용도

- 사람의 검토 없이 행정처분·허가·신고 의사결정을 자동화하는 용도
- 답변을 법률적 의견서나 규제기관의 공식 해석으로 사용하는 용도
- 자체 평가 90점을 정확도 보증서로 제시하는 용도
- 별표 수치를 원본 확인 없이 최종 판단의 유일한 근거로 사용하는 용도

## 7. 결론

`env_law`는 문제 선정과 방향이 좋고, 공식 API 제한·역할 분리·별표 이중 파싱·실증 데이터라는 의미 있는 기반을 갖춘다. 현재는 **사람의 최종 검토를 전제로 하는 내부 법령 리서치 보조도구**로서 가치가 있다.

다음 단계는 에이전트 수나 반복 횟수를 늘리는 것이 아니라, 골든셋·자동 테스트·구조적 별표 비교·정량 지표를 만드는 것이어야 한다. 이 기반이 준비된 후에 Codex 또는 다른 에이전트 플랫폼으로 이식하면 플랫폼 변경이 실질적인 품질 개선으로 이어질 수 있다.
